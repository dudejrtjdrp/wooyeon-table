# 파트 6. 도메인 이해 (10점)

심사기준: "소셜다이닝 서비스와 운영 문제에 대한 이해도"
PRD: Part1 전체(서비스 소개, 성과, 현재 운영 방식, 해결할 문제, 최종 질문), 1~3장(요약·문제·목표·지표), 12장 상태값, 13장 데이터, 15장 예외, 16장 비기능. 온보딩 전체.

## PRD가 원하는 것

- 서비스의 본질: "처음 보는 4~6명이 나와 결이 맞는 사람들과 한 테이블에서 저녁을 먹도록 연결". 기존 선택지(동호회=주기 참여 부담, 소개팅=연애 목적 부담, 대규모 모임=대화 밀도 낮음, 랜덤 만남=안전·품질 불확실)의 빈틈을 메운다(온보딩).
- 현재 운영 방식(Google Forms → 수기 매칭 → 2일 전 카톡방·식당 안내 → 1일 전 리마인드 → 식사 → 콘텐츠 → 피드백 → 다음 매칭 참고)을 **그대로 자동화로 옮긴 흔적**이 보여야 한다.
- 실제 숫자 감각: MVP 243건 신청 → 142명 참가(58.4%), 재방문 15.5% / 온보딩 300명 → 165명(55.0%), 재방문 17.0%. 이탈 지점은 신청 후·결제 후·노쇼. 운영 리스크는 "노쇼와 취소가 한 테이블에 큰 영향을 미치고 CS 문제로 이어짐".
- 상태를 **분리**해서 저장: 신청·결제·매칭·참석을 한 값으로 합치면 충돌한다(온보딩).
- 신뢰성 3종: 멱등성, 감사 로그, 재시도.
- 성과 측정: 획득·전환 / 매칭 품질 / 반복 참여 / 운영 효율을 같은 화면에서(온보딩).
- 개인정보·안전: 연락처·생년·차단·신고·사람별 선호는 필요한 사람만, 운영자 권한 통제, 삭제 요청·탈퇴 후 보관 정책 정의.

## 상태값 (12장) — 그대로 구현됐는지

- application_status: DRAFT, SUBMITTED, CANCELED
- payment_status: PENDING, PAID, FAILED, REFUND_AVAILABLE, REFUND_REQUESTED, REFUND_PROCESSING, REFUNDED, REFUND_FAILED
- match_status: WAITING, MATCHING, REALLOCATING, CONFIRMED, ALTERNATIVE_OFFERED, TRANSFERRED, NO_MATCH, EXCEPTION
- attendance_status: SCHEDULED, ATTENDED, CANCELED_EARLY, CANCELED_LATE, NO_SHOW

## 데이터 (13장) — 엔티티와 핵심 필드

User / Profile(출생연도·성별·직업·MBTI·관심사·본인 성향·희망 상대 성향·식사 조건) / EventSlot(날짜·시간·지역·정원·신청 마감·자동 매칭 실행 시각) / Application(회차 후보·희망 지역·이용권·신청·결제·매칭 상태) / MatchRun / DiningTable(조건별 점수·자동 확정 상태·재배치 이력) / Venue(가격대·날짜·시간별 수용 인원·예약 상태) / ChatRoom / MatchResolution / ExceptionCase / Attendance / Feedback / SafetyReport / Notification.

## 핵심 지표 (3장) — 13개를 계산할 수 있는 데이터가 있는지

신청 완료율, 결제 전환율, 매칭 성공률, 자동 확정률, 자동 재배치 성공률, 대체 일정 전환율, 자동 환불 완료율, 실제 참가 전환율, 노쇼율, 재방문율, 피드백 응답률, 운영자 개입률, 운영 시간.

## 예외 (15장) 10개 — 각각 제품 동작이 있는지

최초 조합 4명 미만 / 같은 조건 다른 테이블 없음 / 확정 후 1명 취소(대기자 충원 → 없으면 남은 사람 재배치) / 재배정 후 연령차 초과 / 결제 미완료 / 환불 선택 / 식당 배정 실패 / 당일 취소·노쇼 / 안전 신고 / 피드백 미응답.

## 흔한 함정

- 결제 상태와 매칭 상태를 하나의 status로 합침.
- 지표를 KPI 카드로만 보여 주고 정의(분자·분모)가 PRD와 다름.
- 실제 운영 데이터처럼 보이게 PRD에 없는 숫자를 단정적으로 박음.
