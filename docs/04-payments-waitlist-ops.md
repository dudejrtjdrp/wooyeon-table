# 결제, 대기자 자동 전환, 운영자 긴급 수정, 대화 콘텐츠

## 결제 (토스페이먼츠)
- 결제 화면에서 토스 결제창(v2, `requestPayment`)을 연다. 카드는 통합결제창, 카카오페이·네이버페이·토스페이는 간편결제 자체창.
- 주문번호 `wt-{payment_id}-{시각}`. 돌아오면 `/api/payments/toss/success`에서 주문번호가 이 결제 건인지, 금액이 서버 기록과 같은지 확인한 뒤 `POST /v1/payments/confirm`으로 승인한다.
- 승인되면 `markPaid`가 결제·이용권·신청 상태를 바꾼다. 대기·실패 상태일 때만 바뀌어서 두 번 돌아와도 한 번만 승인된다.
- 환불은 `refundPayment` 한 곳에서. 토스 결제면 `POST /v1/payments/{paymentKey}/cancel`(멱등 키 `refund-{payment_id}`), 실패하면 `REFUND_FAILED` + 예외 처리함에 올리고 운영자가 "환불 다시 요청"으로 재시도한다.
- 키: `TOSS_CLIENT_KEY`/`TOSS_SECRET_KEY`. 비어 있으면 토스 문서 공개 테스트 키로 동작한다. 사업자 등록 후 라이브 키를 넣으면 시연용 버튼(즉시 결제, 실패 보기)은 사라진다.

## 대기자 자동 전환 (STA-07)
- 확정 테이블에서 취소·제외로 빈자리가 생기면, 같은 회차에서 매칭되지 못한(대안 선택 대기) 사람 중 그 일정을 골랐고 나이·제외 관계가 맞는 사람에게 신청 순서대로 한 명씩 묻는다 (`seat_offers`).
- 응답 기한: 지금부터 6시간, 다만 모임 3시간 전까지. 30분도 안 남으면 묻지 않는다.
- 수락: 조건을 다시 확인하고 테이블에 합류, 결제는 그대로 쓴다. 거절·기한 만료·조건 변경: 다음 대기자. 받을 사람이 없으면 기존 인원 부족 정리(재배치/대안 안내)로 넘어간다.
- 기한 만료는 tick에서 처리한다.

## 운영자 긴급 수정 (MAT-14)
어드민 테이블 상세 → 운영자 긴급 수정. 참가자 이동, 참가자 제외(즉시 환불 선택), 테이블 병합(같은 일정, 최대 인원 이하), 테이블 분리(두 쪽 모두 최소 인원 이상, 새 테이블은 식당 배정·단체방·리마인드 자동), 테이블 해제.
사유 필수, 모든 변경은 `status_events`에 `admin:{id}`와 `[운영자 긴급 수정] 사유`로 남고, 관련 참가자에게 알림과 단체방 공지가 나간다. 나이 차이·차단 관계는 여기서도 완화하지 않는다.

## 대화 콘텐츠 관리 (CON-04)
어드민 → 대화 콘텐츠. 주제·아이스브레이킹 등록·수정·노출 중지, 관심사 태그, 테이블 유형(첫 참가 위주·재방문 위주·4인·5~6인·20대·30대 이상), 우선순위.
노출 규칙(`settings.content.rules`): 주제 개수(3~6), 아이스브레이킹 개수, 관심사 가중치, 유형 가중치. 테이블 상세에서 실제로 나갈 콘텐츠를 미리 볼 수 있다.
대화 성향(CON-02): 테이블 사람들의 MBTI E/I 비율(MBTI가 없으면 '본인 성향'의 유쾌한·리액션 좋은·에너지 넘치는 / 차분한·다정한·진지한)로 '말하기 좋아하는 분이 많은 테이블'(60% 이상)·'차분한 분이 많은 테이블'(40% 이하)·'섞인 테이블'을 정해 테이블 유형에 넣는다. 성향별 기본 주제·아이스브레이킹이 코드에 있고(`lib/contents.ts TONE_CONTENTS`), 운영자가 같은 유형으로 콘텐츠를 등록하면 함께 순위를 매긴다. 주제 중 하나는 꼭 성향에 맞춘 것으로 고른다. 그래서 관심사가 같아도 테이블 분위기가 다르면 다른 주제가 나간다(테스트 `lib/contents.test.ts`).

## 자동 처리 주기와 발송 재시도 (INF-08)

**자동 처리(`tick`)가 도는 때**
- GitHub Actions가 10분마다 `/api/cron/tick`을 부른다(`.github/workflows/tick.yml`). Vercel Cron은 Hobby 요금제라 하루 한 번만 되므로 백업으로 남겼다.
- 참가자 홈·어드민 홈을 열 때도 화면을 먼저 보낸 뒤 돌린다(`maybeTick`). 2분 안에 이미 돌았으면 건너뛰고, 여러 요청이 동시에 와도 `settings.tick.claim`을 먼저 바꾼 한 곳만 돈다.
- 그래서 화요일 24:00 마감 뒤 매칭은 늦어도 10분 안에 돈다(예전엔 다음 날 정오). 하루 전 리마인드와 모임 시작 콘텐츠도 10분 안에 나간다.
- 어드민 홈에 마지막 실행 시각과 '알림 N건 다시 보내는 중'을 보여 준다.

**발송 재시도 — 실패는 자동으로, 반복 실패만 운영자에게**

| 갈래 | 실패를 아는 방법 | 이력 | 재시도 | 3번 실패하면 |
|---|---|---|---|---|
| 앱 알림함 | 저장 오류 | 바로 0.4초 뒤 한 번 더. 예약 알림은 `notifications.attempts`·`last_error`, `status_events(notification, status)` | 예약 알림은 매 실행마다 | `failed` + 예외 `notification` |
| 휴대폰 푸시 | 등록 기기가 있는데 한 대도 못 받음(만료 구독 404·410은 지우고 실패로 안 셈) | `attempts`·`last_error='푸시 실패: …'`, `status_events(notification, push)` | 실패 횟수×10분 뒤, 하루 안 | 예외 `notification`(ref `notification`). 알림함에는 이미 있음 |
| 단체방 안내 | 메시지 저장 오류 | 바로 한 번 더, 그래도 안 되면 `status_events(chat_room, system_message, FAILED)`에 다시 보낼 내용까지 | 마지막 실패 10분 뒤, 하루 안. 성공하면 `SENT` 한 줄 | 예외 `notification`(ref `chat_room`) |

- 같은 메시지는 중복 방지 키(`dedupe_key`)로 한 번만 올라가므로 몇 번을 다시 보내도 두 번 보이지 않는다.
- 운영자는 예외 처리함에서 '다시 보내기'(성공하면 자동으로 닫힘) 또는 '직접 연락함'을 고른다.
- 코드: `lib/delivery.ts`(재시도·예외), `lib/push.ts`(기기별 결과), `lib/notify.ts`(알림함 저장), 테스트 `lib/delivery.test.ts`.

## 실패를 스스로 복구하는 것들 (2026-10-16)

정상 흐름에서 운영자가 손대지 않게, 자동으로 다시 해 보고 끝내 안 될 때만 예외 처리함에 올린다. 전부 `tick`(10분마다)이 돈다.

|---|---|---|---|
| 식당 예약 | 10분 간격 3번 시도(전화 예약 식당은 자동 예약이 안 돼 바로 다음으로) → 그 식당을 빼고 같은 동네·일정의 다른 식당으로 다시 배정·예약. 바뀌면 단체방과 알림으로 알림 | 후보 식당이 모두 안 될 때 (`reservation`) | `lib/reservations.ts`, `lib/pipeline.ts reassignVenue`, `lib/venue-pick.ts` |
