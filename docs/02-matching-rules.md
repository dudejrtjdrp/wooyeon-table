# 02. 매칭 규칙

자동 매칭 엔진이 따르는 규칙. 코드(`src/lib/matching/`)는 이 문서를 그대로 옮긴다. 규칙을 바꾸면 이 문서와 `ALGORITHM_VERSION`을 같이 올린다.

근거: PRD 6.4, 7장, CTO 온보딩 8~9쪽.

## 한 줄 요약

**필수 조건을 하나라도 어기는 조합은 절대 만들지 않고, 그 안에서 점수가 가장 높은 조합을 고른다.** 점수가 기준에 못 미치거나 4명이 안 되면 다른 테이블로 옮기고, 끝까지 안 되면 참가자에게 고르게 한다.

## 1. 매칭 대상

차수의 매칭 시각(`rounds.match_at`)이 되면 아래 조건을 모두 만족하는 신청만 가져온다.

- `application_status = SUBMITTED`
- `payment_status = PAID`
- `match_status = WAITING`
- 계정 상태가 `restricted`, `banned`가 아님

결제가 안 된 신청은 후보에서 빼고 결제 기한 안내만 보낸다. (PRD 15장)

## 2. 필수 조건 (하나라도 어기면 확정 불가)

| 조건 | 판정 |
|---|---|
| 일정 | 테이블의 일정(날짜·시간·지역)을 참가자가 신청 때 골랐어야 한다 |
| 인원 | 4명 이상 6명 이하 |
| 나이 | 출생연도 기준으로 가장 나이 많은 사람과 적은 사람의 차이가 8살 이하 |
| 차단 | 둘 중 누구든 상대를 차단했으면 같은 테이블 불가 |
| 신고 | 신고가 접수된 두 사람은 처리 결과와 상관없이 같은 테이블 불가 (PRD 15장: 즉시 분리) |
| 비선호 | 둘 중 누구든 "다시 만나고 싶지 않아요"를 골랐으면 같은 테이블 불가 |
| 중복 배치 | 한 사람은 한 차수에 한 테이블에만 |

재배치 중에도 이 조건은 절대 완화하지 않는다. (PRD 7.3)

## 3. 선호 점수 (0~100점)

PRD 우선순위(연령대 → 성비 → MBTI → 관심사 → 희망 성향)를 가중치 순서로 그대로 반영하고, 마지막에 새로운 사람 비율을 더한다.

| 항목 | 기본 가중치 | 계산 | 참가자에게 보여줄 말 |
|---|---|---|---|
| 연령대 | 25 | `1 − (나이 차 ÷ 8)` | "비슷한 또래예요" |
| 성비 | 22 | `1 − |남 − 여| ÷ 인원` | "성비가 고르게 맞춰졌어요" |
| MBTI 궁합 | 18 | 두 사람씩 짝지어 아래 표로 점수를 매기고 평균 | "대화 템포가 잘 맞을 조합이에요" |
| 공통 관심사 | 15 | 두 사람씩 겹치는 관심사 수를 보고 평균 (2개 겹치면 만점) | "○○, △△에 관심 있는 분들이에요" |
| 희망 성향 | 12 | 각자가 원한 성향을 가진 사람이 테이블에 있는 비율의 평균 (절반이 넘으면 만점) | "원하신 '○○한 사람'이 함께해요" |
| 새로운 사람 | 8 | 이전에 같이 참석한 적 없는 쌍의 비율 | "모두 처음 만나는 분들이에요" |

가중치와 최소 점수는 `settings` 테이블의 `matching.weights`, `matching.min_score`에서 읽는다. 운영자가 어드민에서 바꿀 수 있다. (MAT-15, P1)

**최소 점수 기본값: 55점.** 필수 조건을 다 지켰는데도 55점 미만이면 확정하지 않고 재배치로 보낸다.

### MBTI 두 사람 점수

복잡한 궁합표 대신 설명할 수 있는 규칙 네 줄로 정한다.

| 비교 | 점수 |
|---|---|
| N/S가 같다 (관심 주제가 비슷) | +0.4 |
| E/I가 다르다 (말하는 사람과 듣는 사람이 섞임) | +0.3, 둘 다 E면 +0.2, 둘 다 I면 +0 |
| J/P가 같다 (약속·진행 방식이 비슷) | +0.2 |
| T/F | +0.1 (어느 쪽이든) |

MBTI를 입력하지 않은 사람이 있으면 그 쌍은 0.5로 둔다.

### 이전 만남과 피드백 반영

- **새로운 사람 우선 (MAT-06)**: 점수의 "새로운 사람" 항목으로 반영한다.
- **다시 만나고 싶어요**: 같은 테이블이면 쌍마다 +2점 (최대 +6점). 단, "새로운 사람" 점수는 그대로 깎인다.
- **다시 만나고 싶지 않아요**: 필수 조건으로 제외한다.
- **만족도**: 지난 테이블에서 분위기·대화 점수를 높게 준 사람들의 공통점(관심사·MBTI 축)은 P2(MAT-16)에서 가중치 학습에 쓴다. 이번 MVP에서는 저장만 한다.

## 4. 처리 순서

```
1. 대상 신청 불러오기 (1장)
2. 제외 관계 목록 만들기 (차단·신고·비선호)
3. 첫 배치: 각자 고른 일정 중 사람이 가장 많이 몰린 곳부터 채운다
4. 일정별 묶기: 나이순으로 정렬해 8살 안쪽 무리를 만들고, 그 안에서 점수가 가장 오르는 사람을 한 명씩 더한다
5. 분리: 7명 이상이면 4~6명 테이블 여러 개로 나눈다 (예: 9명 → 5+4, 13명 → 5+4+4)
   맞바꾸기: 테이블끼리, 테이블과 남은 사람 사이에서 한 명씩 바꿔 보고 낮은 쪽 점수가 오르면 바꾼다
6. 검증: 4명 미만이거나 필수 조건 위반이거나 55점 미만인 테이블을 해제한다
7. 재배치: 해제된 사람을 아래 순서로 다른 테이블에 넣어본다
8. 병합: 합쳐서 4~6명이 되고 조건을 지키는 미완성 테이블끼리 합친다
9. 재검증: 모든 테이블을 다시 확인한다
10. 확정: 통과한 테이블을 자동 확정한다
11. 실패: 끝까지 자리를 못 찾은 사람은 ALTERNATIVE_OFFERED
```

### 재배치 순서 (PRD 7.4)

1. 같은 날짜·같은 지역의 다른 미확정 테이블
2. 같은 날짜·고른 다른 지역의 미확정 테이블
3. 고른 다른 날짜·같은 지역의 미확정 테이블
4. 고른 다른 날짜·다른 지역의 미확정 테이블
5. 그래도 없으면 고르지 않은 다른 모집 일정을 **추천만** 한다 (이동은 참가자가 동의해야 함)

후보 테이블이 여러 개면 넣었을 때 점수가 가장 높은 곳을 고른다. 6명이 꽉 찬 테이블에는 넣지 않는다.

### 일정당 테이블 수

일정마다 최대 테이블 수(`slots.max_tables`)를 넘기지 않는다. 넘치는 사람은 재배치 대상으로 보낸다. 식당 재고는 확정 뒤 배정 단계에서 확인하고, 모자라면 예외 큐(식당 부족)로 보낸다. (PRD 8장 INF-02)

## 5. 확정 뒤 바로 이어지는 일

테이블이 확정되면 같은 트랜잭션 흐름 안에서 아래를 순서대로 실행한다. 각 단계는 중복 방지 키를 써서 두 번 실행돼도 한 번만 일어난다.

1. 참가자 상태: `match_status = CONFIRMED`, `attendance_status = SCHEDULED`
2. 확정 알림 (INF-01)
3. 식당 자동 배정 (INF-02) → 실패 시 예외 큐
4. 단체방 생성과 첫 공지 (INF-04, INF-05)
5. 하루 전 리마인드와 시작 시각 대화 콘텐츠를 예약 (INF-07, CON-03)

## 6. 매칭 결과 설명 (MAT-12, PRD 7.2)

### 참가자에게 보여주는 것

- 적용된 기준: "같은 날짜·지역을 고른 분들 중에서, 또래이면서 성비가 맞도록 묶었어요"
- 함께 묶인 이유: 위 3장 표의 "참가자에게 보여줄 말" 중 점수가 높은 상위 3개
- 재배치·실패 이유: "처음 테이블이 3명이라 같은 날 강남 테이블로 옮겼어요"
- 다른 사람의 나이·MBTI·점수 같은 상세 정보는 보여주지 않는다.

### 운영자에게 보여주는 것 (PRD 7.2 전부)

인원수, 일정 충족 여부, 최고·최저 나이와 차이, 성비, MBTI 구성, 공통 관심사, 희망 성향 충족 여부, 이전 만남 여부, 제외 관계 충돌 여부, 항목별 점수, 재배치 횟수와 최종 사유, 확정·실패 시각.

## 7. 중복 실행 방지

- 차수마다 `match_runs`는 하나만 만들 수 있다(`unique(round_id)`). 스케줄러가 두 번 돌아도 두 번째는 기존 결과를 그대로 돌려준다.
- 단체방은 테이블당 하나(`chat_rooms.table_id unique`), 시스템 공지·알림·예외는 `dedupe_key`로 막는다.
- 환불은 결제 건의 상태를 `PAID → REFUND_REQUESTED`로 바꾸는 조건부 업데이트가 성공했을 때만 진행한다.

## 8. 시연용 가상 시각

심사위원이 마감 시각까지 기다릴 수 없어서, 서버가 보는 "지금"을 `app_clock.offset_seconds`만큼 앞당길 수 있게 한다. 스케줄러와 화면이 모두 이 시각을 기준으로 움직인다. 실제 운영에서는 0이다.
