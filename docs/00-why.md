# 00. 왜 이렇게 만들었나 — 지금 운영 방식과 숫자에서 출발

우연한 식탁은 처음 보는 4~6명이 결이 맞는 사람들과 한 테이블에서 저녁을 먹도록 잇는다. 기존 선택지의 빈틈을 메우는 자리다: 동호회는 주기적으로 나가야 하는 부담, 소개팅은 연애 목적이라는 부담, 대규모 모임은 대화가 얕고, 랜덤 만남은 안전과 품질을 믿기 어렵다. 그래서 한 번만 가볍게, 소수로, 조건을 맞춰, 운영팀이 끝까지 챙기는 모임을 만든다.

지금은 이 운영이 사람 손으로 돌아간다. 이 서비스는 그 순서를 바꾸지 않고, 각 단계를 자동으로 옮겼다.

## 지금 운영 방식 → 서비스에서 맡는 곳

| 지금 (수기) | 서비스에서 | 문서·코드 |
|---|---|---|
| 구글 폼으로 신청, 입금 문자로 결제 확인 | 앱에서 일정·동네를 골라 신청하고 토스로 결제. 결제를 안 하면 결제 안내 알림 | `src/app/apply`, `docs/04` |
| 운영자가 신청서를 보고 수기 매칭 | 회차의 매칭 시각(환불 마감, 모임 주 화요일 24시)에 자동 매칭. 나이 차 8살 이하와 비선호 제외는 반드시, 성비는 점수로 맞추고 지난 만남은 되도록 피함 | `src/lib/matching/`, `docs/02` |
| 2일 전 카톡방을 만들고 식당 안내 | 테이블이 확정되면 평점·예약 가능한 식당을 자동 배정하고 단체방을 연다 | `src/lib/pipeline.ts` |
| 1일 전 리마인드 | 정해진 시각에 자동 리마인드, 보내기가 세 번 실패하면 예외 처리함 | `docs/04` 자동 처리 주기 |
| 식사, 대화 콘텐츠 | 체크인, 모임 시작에 맞춰 대화 콘텐츠 | `src/lib/attendance.ts` |
| 피드백을 받아 다음 매칭에 참고 | 피드백·신고·차단이 다음 매칭 입력으로 들어간다 | `docs/02` |
| 이 모든 것을 여러 도구에서 | 운영자 어드민 한 곳(회차·식당·신청자·결제·예외·변경 이력) | `src/app/admin` |

## 숫자에서 나온 결정

PRD에 있는 숫자: MVP 243건 신청 → 142명 참가(58.4%), 재방문 15.5%. 온보딩 300명 신청 → 165명 참가(55.0%), 재방문 17.0%. 이탈 지점은 신청 후, 결제 후, 노쇼다.

이 숫자들은 어드민 `/admin/metrics`에서 같은 정의로 잰다: 신청→참가는 '실제 참가 전환율'(제출한 신청 중 체크인한 건), 재방문은 '재방문율', 이탈 지점은 '결제 전환율'·'매칭 성공률'·'노쇼율'.

| 이탈 지점 | 그래서 만든 것 |
|---|---|
| 신청 후 결제 전 | 결제 안내 알림, 결제 전에 매칭 시각이 지나면 "빠져나간 돈은 없어요"로 정리 |
| 결제 후 매칭 실패 | 매칭 실패하면 빈자리·다른 일정·자리 기다리기·이용권 보관·환불 중에 참가자가 고른다. 멤버십은 기간을 늘린다 |
| 취소·노쇼가 한 테이블을 흔듦 | 환불 마감(화요일 24시)을 한 곳에서 계산, 당일 취소 불가. 빈자리는 대기자에게 먼저 묻고, 4명 아래로 줄면 같은 조건의 다른 테이블로 옮기거나 선택지를 준다. 노쇼는 90일 기준으로 안내 → 30일 제한 → 운영 검토 |
| 낮은 재방문 | 모임 뒤 다음 일정 추천, 멤버십(기간 안 무제한) |
| CS로 번지는 운영 실수 | 되돌릴 수 없는 동작은 한 번 더 묻고, 누가·언제·무엇을 바꿨는지 변경 이력에 남긴다. 상태값 4종을 따로 둬서 "어디서 멈췄는지"가 보인다(`docs/01`) |
